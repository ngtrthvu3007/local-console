# Development

For people working on Local Console itself. To run and use it, see the [README](../README.md).

## Setup

Requires Node.js 24+ and Docker.

```bash
npm install
docker compose up -d floci   # Floci only
npm run dev:server           # terminal 1: API on :3701
npm run dev:web              # terminal 2: UI on :5173 (proxies /api and /aws to :3701)
```

Checks: `npm run typecheck` · `npm test` (unit tests of `server/` and `web/`)

Integration, E2E, UI, UX and mobile suites run against a running console: see [tests/README.md](../tests/README.md).

## Project layout

```text
server/   Node API: proxies /aws to Floci, /api for what AWS has no API for (Redis keys, RabbitMQ, health)
web/      React + Cloudscape UI
  src/registry.ts        every service is one entry: sidebar, router and search read from it
  src/services/<id>/     one folder per service (pages, components, hooks, routes)
  src/shared/            layout, shared components and hooks
tests/    black-box suites against a running console (it, e2e, ui, ux, mobile)
docs/superpowers/        design specs, plans, roadmap
```

Adding a service = one folder in `web/src/services/` and one entry in `registry.ts`. How a service goes from spec to release: [roadmap, section 8](superpowers/roadmap.md). Main design: [docs/superpowers/specs/2026-11-09-localconsole-design.md](superpowers/specs/2026-11-09-localconsole-design.md).

## Traps & open issues

- **SNS email / SMS subscriptions never deliver on Floci.** `Subscribe` with `sms` or `email` succeeds but stays `PendingConfirmation` (`ConfirmSubscription` rejects any token), and `Publish` to the topic writes nothing to the SMS inbox or the SES mailbox (checked 2026-11-21). The subscription modal only offers SQS / Lambda / HTTP(S). Publishing straight to a phone number (SNS › SMS) works.
- **CloudFormation: "Stack: X" on service pages comes from an index.** `StackLink` (`web/src/shared/StackLink.tsx`) looks a resource up in an index built from `DescribeStacks` + `ListStackResources` of every stack (not `DescribeStackResources?PhysicalResourceId=`, which answers 400 for a resource outside any stack and makes the browser log a `console.error`). One query per 30 s (`RESOURCE_INDEX_STALE_MS`), so it is slow with hundreds of stacks and a stack created a moment ago may not show for up to 30 s. The CloudFormation SDK loads lazily inside that query: keep it out of `shared` and `registry.ts` imports. The delete flow polls `DescribeStacks` without a name for the same 400 reason.
- **A `CREATE_COMPLETE` stack on Floci may not deploy on AWS.** Floci stubs resource types it doesn't support (`AWS::AmazonMQ::Broker`, `ElastiCache::ReplicationGroup`, `Glue::*`, …): the stack succeeds but nothing is created. The reason ("was stubbed and nothing was created") exists only in the events, so the stack page shows a warning and a "Stubbed by Floci" badge from them. `Ref` to an undeclared parameter becomes a literal string; `OnFailure`, `DisableRollback` and `RetainResources` are ignored.
- **Deleting by hand a resource a stack made leaves the stack `CREATE_COMPLETE`**, and creating it again by hand with the same name makes `DeleteStack` delete it too. A queue deleted by hand can also make a later `DeleteStack` end in `DELETE_FAILED` (seen 2026-11-22), so `tests/it/leftovers.mjs` deletes stacks first. A bucket that still has objects makes `DeleteStack` fail with `DELETE_FAILED`.
- **CDK apps with Node custom resources (`autoDeleteObjects`, `BucketDeployment`, `AwsCustomResource`, `logRetention`) fail to deploy with `ECONNREFUSED …:443`** unless Floci runs with TLS: `FLOCI_TLS_ENABLED=true docker compose up -d` (off by default in `docker-compose.yml`). With it on, the URLs Floci returns (SQS `QueueUrl`, queue physical IDs) become `https://` with a self-signed certificate. The Events tab hints at this when it sees that error.
- **"Other senders" blocks scan the browser-side.** Queue / topic / function pages list S3 notifications, Lambda async destinations, trigger on-failure destinations and SES configuration sets that point at them, by listing buckets, functions and configuration sets when the page opens (`web/src/services/integrations/senders.ts`). Fine for a local Floci; slow with hundreds of functions.
- **An SES configuration set sends to the default event bus only.** `CreateConfigurationSetEventDestination` with another bus ARN fails (`EventBridgeDestination EventBusArn must be a valid default event bus ARN`), the same as on AWS. The destination modal lists only `default`; catch the events with a rule on it for source `aws.ses`. Reading an identity with no default set returns no `ConfigurationSetName`, so the hook stores `""` (React Query rejects `undefined`).
- **`/api` and `/aws` only answer the console itself.** `server/src/middleware/localOnly.ts` rejects (403) requests from another site (`Sec-Fetch-Site`) and foreign `Host` headers (DNS rebinding). Open the console via `localhost`, `127.0.0.1` or `[::1]`; any other hostname gets 403. `/api/health` stays open for Floci's probe. Floci's own port `4566` is not covered.
- **Each service's pages load lazily (`lazyPage` in `web/src/shared/lazyPage.ts`).** The main chunk is ~750 KB JS (gzip ~215 KB) and ~515 KB CSS; a service's SDK and pages load when you open it. Keep it that way: a new service's routes use `lazyPage`, and nothing in `registry.ts` or the shared layout may import a service's SDK hooks (that would pull its SDK back into the main bundle). The same goes for `zod` (~90 KB) and Cloudscape's `applyTheme` (~600 KB): button tokens are set as CSS variables in `Layout.css` instead, and `test/shared/buttonTokens.test.ts` fails when a Cloudscape upgrade renames them. Served uncompressed: compression skipped while the console is localhost-only.
- **Logo `<img>` has no `width`/`height` (2 perf WARNs, won't fix):** Cloudscape `TopNavigation` renders it and its `logo` prop only takes `src`/`alt`; `mark.svg` already has a fixed size and layout shift is 0.
- **E2E fails on any `console.error` (`tests/e2e/fixtures.ts`).** The only exceptions are S3's 404 for a bucket without lifecycle/tags (`?lifecycle`, `?tagging`): S3 answers "not configured" with 404, the app shows it as empty, but the browser still logs the request. Don't widen the filter; avoid the error instead (e.g. Lambda Monitor checks `DescribeLogGroups` before `FilterLogEvents`).
- **Floci doesn't clean up references.** Deleting a function, queue or topic leaves S3 notification rules, SNS subscriptions and Lambda triggers pointing at it. The console shows them as "(not found)" (`Link` components probe the target), the S3 properties tab offers "Remove broken rules" (S3 rejects every save while one exists), the queue / table trigger lists offer "Remove broken triggers" (`BrokenTriggersAlert`), and the delete modals warn first (`useReferencedNames`). Deleting a function also deletes its queue/stream triggers by default: Floci keeps them, and they run again if a function with the same name is created. Deleting a DLQ makes Floci drop the source queue's failed messages for good.
- **Floci accepts integrations AWS rejects; the console blocks them instead:** overlapping S3 notification filters for the same event type (`overlappingRule`), a second trigger for the same queue/stream and function (`ALREADY_TRIGGERED`), standard topic → FIFO queue and FIFO topic → Lambda/HTTP subscriptions. Anything created outside the console (CLI, IaC) can still have them. Probing a deleted target makes the browser log a 400/404 `console.error`, so an E2E that deliberately leaves dangling references needs an exception like the S3 one above.
- **MQ queues/exchanges don't load in dev mode on macOS/Windows.** Floci returns the broker's `ConsoleURL` as the RabbitMQ container's Docker IP (`http://172.x.x.x:15672`). The console in `docker compose` reaches it; `npm run dev:server` on the host can't (Docker Desktop doesn't route container IPs), so `/api/mq` answers 502 `BrokerUnavailable` and `it/mq.test.ts` times out. Run the console with `docker compose up --build -d console` (keep `npm run dev:web` for the UI) when working on MQ. Linux hosts route container IPs and are fine.
- **The first use of some services downloads more images.** `docker compose up` pulls Floci itself (~270 MB). Floci then pulls on demand: the Lambda runtime on the first invoke (Node.js ~440 MB), Valkey on the first ElastiCache cluster (~130 MB), RabbitMQ on the first MQ broker (~270 MB), `postgres:16.3-alpine` (~250 MB) / `mysql:8.0.36` (~620 MB) on the first RDS database of that engine (`CreateDBInstance` waits for the pull). That first call is slow, and fails offline.
- **When Floci is down, every page except Home shows "Floci isn't running"** with the start command (`Unavailable.tsx`); the page underneath stays mounted (hidden), so unsaved edits survive. With `npm run dev:web` and no API server, it shows "Can't reach the console server" instead.
- **MQ quirks come from Floci, not the console.** `RebootBroker` returns success without restarting the container (the console only asks for confirmation). The RabbitMQ container is published on `0.0.0.0`, not `127.0.0.1` like Redis, on the first free port of 5672–5699 (it may be 5673) and 15672–15699.
- **SNS text messages can't be deleted one by one.** Floci's `DELETE /_aws/sns` only clears the SMS inbox of every region; unlike SES's `DELETE /_aws/ses`, it takes no `?id=` (by design: the endpoint is a test helper), so the SMS page only has "Delete all" (with a warning), and the SMS tests never clean up after themselves (`it/leftovers.mjs` only lists them). `GET /_aws/sns` does accept `?phone=` and `?id=`.
- **`awslambda-<region>-tasks` bucket.** Floci creates it with the first function and it shows in the S3 bucket list; the console doesn't hide it.
- **ElastiCache "Created" and node status show "—"** because Floci doesn't return them.
- **Terminated EC2 instances stay in the list.** Floci 2.4.0 keeps them in `DescribeInstances` (instances terminated on 2026-11-19 were still listed on 2026-11-25), unlike AWS which drops them after about an hour; filter by state to hide them.
- **RDS databases are real PostgreSQL / MySQL containers.** Compose publishes `127.0.0.1:7001-7099` so the dev machine reaches them at `localhost:<port>`; the endpoint Floci returns (an IP in the compose network) only works from Lambda and apps in the compose. Don't set `FLOCI_SERVICES_RDS_ENDPOINT_HOST=localhost`: Lambda then can't reach the database. The same compose IP is what `GetAtt Endpoint.Address`, an SSM parameter holding it and the `host` of an `rds!` secret contain, so an app on a macOS / Windows host that reads its host from there can't connect: override it with `localhost:<port>` (the Connect card's `DB_HOST` / `DB_PORT`). `{{resolve:ssm}}`, `{{resolve:ssm-secure}}`, `{{resolve:secretsmanager}}` and `/aws/reference/secretsmanager/` all work with RDS (checked 2026-11-23). Deleting a database leaves its Docker volume (`floci-aws-rds-db-…`, hybrid storage), so IT / E2E runs pile them up: remove with `docker volume rm`. A database made by CloudFormation has no `EngineVersion` and Floci 2.4.0 ignores `ManageMasterUserPassword` there (no `rds!` secret); `CreateDBInstance` returns both. A missing database answers 404 `DBInstanceNotFound`. Floci accepts master passwords AWS rejects (`/ ' " @`, spaces, MySQL over 41 characters) and they log in, so the create form checks the AWS rules itself. Floci answers `available` as soon as the container runs, before the database accepts logins: MySQL needs about 5–8 s more (`Lost connection … reading initial communication packet`), so the create message says so. Restarting or recreating Floci restarts its database containers with their data, stopped ones stay stopped (checked 2026-11-23). An identifier with capitals keeps them in Floci (AWS lowercases it); lookups ignore case.
- **EC2 VPC networks are off (`FLOCI_SERVICES_EC2_VPC_NETWORKS_ENABLED: "false"` in `docker-compose.yml`).** With them on, launching an instance attaches the Floci container to a Docker network per VPC (`floci-aws-vpc-…`), and Docker keeps that attachment across restarts. When Floci starts while attached (`docker compose restart floci`, Docker Desktop or machine restart) it picks the VPC network for Lambda containers, while its DNS listens only on the compose network: inside Lambda `localhost.floci.io` resolves to `127.0.0.1`, so every SDK call fails with `ECONNREFUSED 127.0.0.1:4566` (secret rotation, Lambda calling SQS / DynamoDB…). `FLOCI_SERVICES_DOCKER_NETWORK` doesn't help (checked 2026-11-25). With VPC networks off, instances join the compose network and still reach RDS. A Floci started with the old setting: `docker network disconnect <floci-aws-vpc-…> local-console-floci-1`, then `docker compose up -d --force-recreate floci`. Remove the setting once Floci picks its DNS network for Lambda.
- **EC2 instances look Running after Floci restarts, but their containers are stopped.** `docker compose restart floci`, or Docker Desktop / machine restart, kills instance containers (`Exited (137)`) while `DescribeInstances` still says `running`, so the console shows Running too (checked 2026-11-25). Floci doesn't reconcile it, and Reboot answers success without starting the container. Stop (~30 s) then Start brings it back; processes from user data don't run again (spec EC2 7 #3). RDS databases come back by themselves.
- **AppSync in Floci 2.4.0 (checked 2026-11-25).** Schema, NONE / DynamoDB / Lambda data sources, JS and VTL resolvers, pipelines and queries with an API key, Cognito or IAM run for real; subscriptions (WebSocket), `EvaluateCode` / `EvaluateMappingTemplate`, caching and merged / event APIs don't exist. Differences the console works around: `GetIntrospectionSchema` returns the SDL wrapped in JSON (`{"schema":{"definition":…}}`, AWS sends it bare) and 404 for an API without a schema, so Create API saves a sample schema at once; `ListTypes` is always empty (types come from the SDL); schema errors report lines ~27 too high (the console drops them); Cognito needs `Authorization: Bearer <token>` (a bare token is 401) and `@aws_cognito_user_pools` needs `cognito_groups`; IAM through the `/aws` proxy must be signed for the host and path of `uris.GRAPHQL` (`localhost.floci.io:4566/v1/…`); a Lambda resolver without code (direct) sends the function an empty event, so resolvers always send an `Invoke` request; HTTP data sources fail at query time; Floci lets you delete a data source or function still in use and `ListResolversByFunction` is always empty (the console checks usage itself). Code is not checked when saved: errors show when a query runs. The first query starts two containers, `floci-aws-graphql` and `floci-aws-appsync-js-runtime`, publishing random ports on `0.0.0.0` (the JS runtime answers without auth); they keep running after every API is deleted. The console can't change this: stop them by hand when you don't need them.
- **CloudFront in Floci 2.4.0 (checked 2026-11-25).** Floci serves distributions for real (default root object, error pages, behaviors in order, origin path) but never caches, so invalidations complete at once, and it reports `Status: Deployed` always. The console builds the local URL as `http://<id>.cloudfront.localhost:<Floci port>/` (Floci returns only `*.cloudfront.net`). It works **from your machine only**: containers in this compose can't resolve it, and Node / Python on Windows or Linux may not resolve `*.localhost` (not checked; browsers do). A custom origin on a private host (`host.docker.internal`, your app) answers 502 until Floci starts with `FLOCI_SERVICES_CLOUDFRONT_ALLOWED_PRIVATE_ORIGIN_HOSTS=host.docker.internal`; it is **not** in `docker-compose.yml` (decided 2026-11-25), the origin form says so. An S3 website endpoint (`<bucket>.s3-website-<region>.amazonaws.com`) as a custom origin is fetched from real AWS. Floci accepts configs AWS rejects (duplicate origin IDs or path patterns, behaviors pointing at a missing origin → 502 "No origin matched the request.", root object starting with `/`, invalidation paths without `/`); the console blocks them. Every save re-reads the config and sends the fresh ETag; Floci rejects a stale one (`InvalidIfMatchVersion`).
- **KMS in Floci 2.4.0 (checked 2026-11-25).** Encrypt / decrypt, data keys, RSA / ECC sign and verify, HMAC and disabled / pending-deletion errors are real. Floci accepts a 6 or 31-day deletion window and a duplicate alias name (the console checks both), and `CancelKeyDeletion` leaves the key Enabled (AWS: Disabled). A missing key answers `NotFoundException` with HTTP **400**, not 404, so `KeyLink` uses `isKeyMissing` and the browser still logs a 400 for a missing key; a wrong signature / MAC also comes back as a 400 error that Try it shows as Invalid — E2E must not trigger either. Secrets Manager, SSM, S3, SQS, SNS, DynamoDB, Lambda and RDS store the key ID but **ignore the key state** (a disabled key keeps working), and Floci doesn't apply a bucket's default encryption to new objects. `ListKeyRotations` is not supported.
- **URLs Floci returns use `localhost.floci.io` (`FLOCI_HOSTNAME` in `docker-compose.yml`).** SQS queue URLs, ElastiCache endpoints, SNS `SubscribeURL`… must work on the host, in this compose and in Lambda containers, and AWS SDK v3 sends SQS calls to the queue URL's host. `localhost.floci.io` resolves to `127.0.0.1` through public DNS, the compose network gives Floci that alias, and Floci's own DNS answers it for Lambda containers. **Offline, or on networks that block DNS answers pointing at `127.0.0.1`, the host can't resolve it:** add `127.0.0.1 localhost.floci.io` to `/etc/hosts`. With the old `localhost` URLs, SQS from a Lambda or a compose app failed with `ECONNREFUSED`.
- **SQS peek needs a region header.** `GET /aws/_aws/sqs/messages` (Floci-only) looks the queue up in Floci's default region unless an `Authorization` header names the console region (`web/src/services/sqs/peek.ts`; signature is not checked).
- **Recently visited services live in the browser** (`localStorage`, key `localconsole:recent-services`, `web/src/shared/recentServices.ts`), like the colour mode (`localconsole:color-mode`). Private windows or blocked storage just start empty every time.
- **"Reset data" (Console Home) calls Floci's `POST /_floci/state/reset`.** It wipes every service in every region, including the SES mailbox and SMS inbox, stops Lambda containers and removes EC2 instance containers (EC2 launches fine afterwards, checked 2026-11-25). Floci 2.4.0 leaves Valkey (ElastiCache), RabbitMQ (MQ) and RDS database containers running with no record left; `docker compose restart floci` removes them, so the modal shows that command (checked on a throwaway Floci, 2026-11-20; RDS 2026-11-23). Until that restart, `CreateDBInstance` fails with `InternalFailure: Failed to start RDS proxy … on port 7001` because the old database still holds the port. Tests never call the real endpoint: `e2e/home.spec.ts` mocks it with `page.route`. Never try it against a Floci holding data you care about.
- **Step Functions quirks in Floci 2.4.0.** The Steps table is built from `GetExecutionHistory` (`web/src/services/stepfunctions/steps.ts`, fixtures of real histories in `web/test/services/stepfunctions/fixtures/`). `Wait` and `Retry` are cut at 30 s. A Distributed Map emits no iteration events, so it shows as one row. When a Map iteration fails, Floci attaches both `MapIterationAborted` and `MapIterationFailed` to the first iteration, so the console takes the error of the failing step inside. The `Fail` state has no exit event: its error comes from `ExecutionFailed`. A Map or Parallel with more than 20 children is collapsed on load. Deleting a state machine leaves its executions in Floci: create one with the same name again and the old executions are listed, and `StartExecution` with an old execution name fails with `ExecutionAlreadyExists` (checked 2026-11-22), so use fresh names in tests. A rule target for a state machine needs no `RoleArn`; a schedule target does (the console sends the default role). Most `aws-sdk:*` task integrations fail with `States.TaskFailed: Unsupported resource` (`aws-sdk:ec2:*` and `aws-sdk:rds:*` checked 2026-11-25; `s3:getObject`, `lambda:invoke` in the spec): have the task call a Lambda function that uses the SDK instead.
- **Kinesis in Floci 2.4.0 (checked 2026-11-25).** Records, iterators (trim horizon, latest, at timestamp) and Lambda triggers are real. A missing stream answers `ResourceNotFoundException` with HTTP **400**, so the browser logs a `console.error`: `StreamLink` checks the `ListStreams` list instead of `DescribeStreamSummary`, and E2E never opens a missing stream. Floci accepts stream names AWS rejects (`bad name!`), so the create form checks them. Deleting a stream keeps its Lambda triggers (the delete modal warns, Lambda › Triggers shows "(not found)"). A Kinesis trigger only returns `State`: no `LastProcessingResult`, `BisectBatchOnFunctionError` or `MaximumRetryAttempts` unless set. The Kinesis SDK on Node uses HTTP/2 by default and fails through the console's `/aws` proxy with `ERR_HTTP2_ERROR` (straight to Floci it works, so app code needs nothing): tests pass `requestHandler: new NodeHttpHandler()` (`@smithy/node-http-handler`, present through every AWS SDK client); the browser uses `fetch` and is fine. EventBridge rules and schedules accept a Kinesis target and report success, but nothing reaches the stream: the console doesn't offer Kinesis as a target and marks existing ones "(Floci doesn't deliver to Kinesis)". Trigger filter patterns (`{"data": …}`) and KMS stream encryption work.
- **ECS in Floci 2.4.0 (checked 2026-11-26).** Tasks are real Docker containers (`floci-aws-ecs-<taskId>-<container>`), images pulled from `public.ecr.aws` on first use (`RunTask` waits for the pull). **Floci keeps no tasks:** restarting it forgets running standalone tasks and every stopped task (`DescribeTasks` → `failures: MISSING`); clusters, task definitions and services stay, and services start new tasks. With a missing cluster, `ListTasks` / `ListServices` / `DescribeTasks` / `DescribeServices` answer 400 `ClusterNotFoundException` (browser `console.error`), and naming `default` in `ListTasks`, `ListServices` or `RunTask` without a cluster makes Floci **create** a `default` cluster: pages ask `DescribeClusters` first (200 + `failures`). `DescribeTaskDefinition` of a missing revision answers 400, so the revision page checks `ListTaskDefinitions` first. `DeleteTaskDefinitions` leaves revisions `DELETE_IN_PROGRESS` forever. `DeleteService` with `force` doesn't stop the service's running tasks (AWS does): scale to 0 and wait, or stop them in the cluster's Tasks tab; a task still `STOPPING` blocks `DeleteCluster` for a few seconds (`ClusterContainsTasksException`). A missing `awslogs-group` is created by Floci (AWS fails the task). An EventBridge rule or schedule with an ECS target and a bad `NetworkConfiguration` reports success and only logs `INVALID_PARAMETER` in Floci: the target forms always send subnets. Fargate task ports aren't published to the host.
- **EventBridge patterns in Floci 2.4.0.** `numeric`, `wildcard` and array values in events never match, in `TestEventPattern` and in real routing; `PutRule` accepts a pattern that isn't JSON, so the console checks it itself. There is no `ListRuleNamesByTarget`, so "which rules point at this queue" has to scan every bus. A schedule's expression isn't in `ListSchedules`, only in `GetSchedule`.
